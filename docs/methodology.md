# 方法论

这套流程不是"想到哪改到哪"攒出来的，每一层都对应一次真实的翻车。

---

## 一、为什么是字节级替换，而不是解析 / 正则重写

线上 chunk 是 Vite 压缩产物。它有三个特点让常规手段失效：

1. **单行。** 几十万字符挤在一行里，报错永远指向"第 1 行"。
2. **含非 UTF-8 字节。** 早期脚本的注释里写过"不触碰文件中的非 UTF-8 字面量"——文件本身
   就不保证是合法 UTF-8。任何"读成 str 再写回"的流程（换行规范化、代理对处理、BOM 插入）
   都可能改变字节。
3. **格式化会破坏语义。** `__vite__mapDeps` 的索引、模块作用域内的短变量名，都依赖精确的
   字符位置。

所以整条链路是 **bytes 进、bytes 出**：`open(path,'rb').read()` → 字面量替换 → `write('wb')`。
只有生成 diff 报告时才 decode，且用 `errors="replace"`。

**代价**：替换片段必须字面精确。**补偿**：命中数断言——如果片段对不上，`count` 会是 0，
立刻报错而不是静默跳过。

---

## 二、为什么"命中数"是整套流程的地基

压缩产物里，`Math.min(100,` 这种片段在别处也会出现。一个真实的教训：

> 原计划断言 `Math.min(100,` 只出现 1 次，实际发现它在本页出现 2 次（成功率图 + 另一张图）。
> 如果按 1 次断言并通过替换，会把另一张图的数值范围一起改掉。

所以引擎强制要求每次替换声明 `count`：

```python
eng.add("成功率上界", b"Math.max(85,Math.min(100,", b"...", count=2)
```

`count` 不符 → 抛 `PatchError`，**且不写任何文件**。

更隐蔽的情况是**片段在别处出现但语义不同**：

```python
eng.add("改 clamp", b"Math.max(85,Math.min(100,", b"R(", count=2)   # 括号数变了！
```

这时**括号配平检查**会拦下（`() 2/4`）。压缩产物里括号数不守恒，几乎一定是片段切错了。

## 三、可逆性自证：比"我改了 5 处"强得多

补丁跑完后，引擎对新内容施加**逆替换**，要求逐字节还原出原文件：

```python
back = new
for e in reversed(edits):
    back = back.replace(e.new_b(), e.old_b())
assert back == src        # 失败即中止
```

这证明两个文件之间的差异**只有**声明的那几处，没有任何附带偏移。

有一个反例能说明它的价值：`A -> B` 而文件里本来就有别的 `B`。逆替换会把那些 `B` 也变回 `A`，
结果不等于原文件，检查失败。如果没这道关，这种"新片段与既有内容撞车"的问题只能在页面上
以诡异的方式暴露出来。

---

## 四、差异区域聚类：让机器输出人眼能核对的改动单

`difflib.SequenceMatcher` 在压缩产物上会把数组、长数字按字符切碎。直接数 opcode 会得到
"27 个字符级差异子段"这种没法核对的结果。

按"相邻差异间隔 < 50 字符就并入同一块"聚类之后，区域数才对得上人眼看到的那几处改动：

```
=== 差异区域 ===
  #1 旧@1234..1250 (16 B) -> 新@1234..1249 (15 B)
      旧: b'current:96.2'
      新: b'current:91.4'
  ...
  合计 5 个区域（字符级差异子段 27 个）
```

于是可以把它变成一条**断言**：`eng.expect_regions(5)`。改动点是 5 处，就应该是 5 个区域；
多一个少一个都说明改到了不该改的地方。

## 五、僵尸副本：为什么"HTTP 200"什么都不能保证

`assets/` 目录里会残留历史构建的同名 chunk：`Module-<hashA>.js`、`Module-<hashB>.js`、
`Module-<hashC>.js`。**改错副本时，一切指标都是正常的**——页面打得开、HTTP 200、文件大小
也对，就是界面毫无变化。

判定活跃副本，按可靠性排序：

1. **引用链可达性**（最可靠）。从入口 `index-*.js` 出发做 BFS，只有被链上文件显式
   `import` 的 chunk 才会被浏览器加载。
2. **`__vite__mapDeps` 索引**。路由懒加载的 chunk 集合由入口里的索引数组决定。
3. **`index.html` 引用**。确认真正生效的入口文件名。

`tgpatch locate` 把这三者合起来用，并显式列出"僵尸副本"。

**⚠️ 入口识别有个坑**：`index.html` 里**第一个** `<script src>` 通常是
`/cesium/Cesium.js`（地图库），不是 SPA 入口。必须按 `index-` 前缀筛。踩过一次：对着
Cesium 文件分析"为什么改不动"。

## 六、为什么要用"顶层路由块边界法"界定改动范围

需求说"AI 任务调度系统里所有 2023 改成 2026"。全局替换会误伤：

| 误伤对象 | 实际是什么 |
|---|---|
| `FarmlandMap-B8wwDWtu.js` | 属于 `/monitoring-center/3d-map`，根本不是调度系统 |
| `index-IpV8ITOi.css` | SVG path 坐标 `%20233.62` |
| `index-DAMuBsXX.js` | 随机数常量数组 `2150032023` |

两步定位：

1. **圈定模块 chunk 全集**：在入口文件里从 `{path:"/task-scheduling"` 扫到下一个顶层路由，
   中间 import 的 chunk 就是该模块的全部页面。
2. **换更精确的字面量**：只替换 `"2023-`（带引号带连字符），即 ISO 日期串前缀。SVG 坐标和
   数字常量天然不受影响。

**结论**：范围界定比替换本身重要。先证明"哪些地方该改、哪些不该改"，再动手。

## 七、三层验证，各管一段

| 层级 | 手段 | 能发现 | 发现不了 |
|---|---|---|---|
| **静态** | 命中数 / 前后置断言 / 可逆性 / 括号配平 / ESM 语法 | 替换文本在不在、语法能否解析 | 文件没被部署；部署到了僵尸副本 |
| **HTTP** | md5 比对、`must`/`mustnot` 文本、入口引用链、路由 200 | 部署是否生效、入口是否真引用该 chunk | 页面渲染出来到底是什么 |
| **浏览器** | playwright 无头 Chrome，读真实 DOM、点按钮、等定时器 | 页面真的显示成什么样、交互行为、同页误伤 | 部署到了别的环境 |

**ESM 语法校验为什么必须单独一层**：替换把括号切错时，浏览器会**整页白屏**，而 HTTP 层
完全看不出问题（文件 200、大小正常、`Content-Type` 也对）。用
`vm.SourceTextModule(src)` 只要求"可解析"、不求值（求值会触发 import、DOM、副作用）。

**浏览器层为什么必须单独一层**：Vue 应用在数据结构与模板不匹配时会**静默不渲染**。静态全绿、
HTTP 全绿、打开页面一片空白——这种情况只有真浏览器能发现。

### 端到端阈值要先算再写

随机行为的断言阈值不能拍脑袋，否则会写出一个"偶尔失败"的测试。改成功率区间时是这样定的：

```python
failure_probability(step_scale=5.0, lo=78, hi=95, margin=0, steps=20)
```

先用蒙特卡洛算出"20 步内越界"的概率，确认是 0，才敢写 `assert 全部在 [78,95]`。
"20 步跨度 >= 8"这条也是先算过失败概率极低才定下来的。

## 八、clamp 为什么会"卡死"

最直觉的区间限制写法是：

```js
v = Math.max(78, Math.min(95, v + delta))     // ❌
```

随机游走一旦贴上边界，下一次的值仍可能越界，于是又被夹回边界——**连续多次输出完全相同的
数值**。实测观察到成功率卡在 `78.0` 整整 5 个采样点、25 秒不动，用户会认为页面卡死。

改用**触边回弹**（以边界为轴镜像）：

```js
v = (_v => _v > 95 ? 190 - _v : _v < 78 ? 156 - _v : _v)(v + delta)   // ✓
```

- 95 是上界 → 镜像轴 `2*95 = 190`
- 78 是下界 → 镜像轴 `2*78 = 156`

越界后立刻朝反方向走，既不出界，也不滞留。写成 IIFE 是为了不引入新变量名——插入的是
压缩产物，多一个顶层标识符就可能与既有短名冲突。

上线前的自证：

```
手动刷新 ±5   2 万步 min=78.00 max=95.00 span=17.00 最长贴边连续=2 步
定时器 ±4     2 万步 min=78.00 max=95.00 span=17.00 最长贴边连续=1 步
✓ 永不越界、覆盖全区间、不滞留边界
```

## 九、部署的可逆性与幂等

`deploy` 的流程：`tar.gz` 打包 → base64 分块上传（避开 `ARG_MAX` 与多层 shell 转义）→
宿主解包 → **容器内备份原文件**（`.bak-<时间戳>`）→ `docker cp` → 容器内逐文件 `md5sum` 比对。

任一步失败都抛异常，且 `md5` 不一致时提示用哪个备份回滚：

```
部署后 md5 不一致: [...]
请用备份后缀 .bak-20261011120000 回滚。
```

`rollback` 子命令一键还原。

## 十、本地副本的"新鲜度"陷阱

**从线上取回的旧副本比没有副本更危险。**

真实事故：某 chunk 在本机留过两份副本，其中一份是改动前的版本（把"果园"写成了"农田"）。
直接拿它当基线，会把之前已经改好的文案**静默回退**——补丁本身完全成功，断言全过，
只是把旧的错误内容又推上线了。

所以每个案例的前置断言里都有这类"我改的是正确的那一份"的证据：

```python
eng.assert_before("本地副本是新版（无「农田」残留）", lambda s: s.count("农田".encode()) == 0)
```

以及流水线化的保障：每次动手前重新 `pull` 并与线上 `md5` 比对。

---

## 十一、把 md5 当回归测试

`tests/test_pipeline.py` 会把每个案例的输出 md5 与**当初部署上线并通过三层验证的版本**
逐一比对。

这一步不可省略。把脚本"整理得更漂亮"的过程中（比如把 `str.replace` 换成 bytes 替换、
把内联断言抽成函数），很容易悄悄改变替换行为。**静态断言、语法校验、HTTP 校验都发现不了
这种偏移**——只有 md5 能。

```
A) 独立案例（输入 -> 输出 的 md5 必须与线上已验证版本一致）
  [OK] 01-picker-success-rate 输出 md5 == 线上已验证版本   2493ad757eb4
  ...
结果: 全部通过 ✓（15/15 通过）
```
